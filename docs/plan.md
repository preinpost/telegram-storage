# Telegram 기반 무제한 파일 스토리지 — 개인 프로젝트 계획서

> 개인 프로젝트(개인 학습/포트폴리오) · 약 **20명 팀원**과 파일 공유 목적
> 핵심 아이디어: **실제 바이너리는 Telegram에, 메타데이터는 DB에** 두고 대용량은 **분할 청크**로 처리한다.

---

## 1. 목표 (Goals)

- 파일 저장 바이너리는 **Telegram(무제한, 무료)**에, 그 **메타데이터(폴더/권한/파일 목록)**는 DB에 분리 저장.
- 개별 파일 최대 크기 제한 없이(분할 청크) 팀원들과 공유.
- 약 20명 대상, 멤버별 **폴더 읽기/쓰기 권한** 지원.
- 개인 프로젝트니까 **학습 + 재미**가 우선, 운영 부담은 최소화.

### 비목표 (Non-Goals)
- 엔터프라이즈급 안정성/보증.
- 텔레그램 로컬 봇 서버(VPS) 운영을 1단계에서 요구하지 않음 (20MB 이하 다운로드 경로로 시작).
- 실시간 동기화/오피스 협업(Nextcloud 수준의 문서 편집 등).

---

## 2. 전체 아키텍처

```
                ┌──────────────────────────────┐
  사용자/팀원 ──▶│  웹앱(프론트) + API 서버        │
                │   - 파일 트리 / 권한 / 검색 UI   │
                └──────────────┬───────────────┘
                               │ REST
                ┌──────────────▼───────────────┐
                │  메타데이터 DB                 │
                │  files / parts / folders /    │
                │  permissions / users          │
                └──────────────┬───────────────┘
                               │ blob 업/다운 (분할)
                ┌──────────────▼───────────────┐
                │  Telegram Bot API             │  ← 무료 저장소(무제한)
                │  (15MB 청크 단위 send/getFile)│
                └──────────────┬───────────────┘
                               │ (선택) 읽기 캐시
                ┌──────────────▼───────────────┐
                │  캐시 계층 (로컬 디스크 / S3)   │  ← 자주 읽는 파일
                └──────────────────────────────┘
```

### 핵심 원칙
1. **Telegram = blob 저장소 전용.** DB가 "무엇이 어디에 있는지"를 안다.
2. **대용량은 분할.** 청크 크기 **15MB** (아래 표 참고) → 공개 Bot API 만으로 동작 → VPS 불필요.
3. **권한은 DB에만.** Telegram 접근 노출 없이 DB가 게이트키퍼 역할.

---

## 3. 왜 15MB 청크인가 (한도 회피 근거)

| 경로 | 공개 Bot API 한도 | 청크 15MB 시 |
|---|---|---|
| 업로드 `sendDocument` | 50MB 이하 | ✅ 통과 |
| 다운로드 `getFile` | 20MB 이하 | ✅ 통과 |

- 15MB 청크면 **업로드·다운로드 양쪽 모두 서버리스(무료)**로 가능.
- 전체 저장량은 텔레그램에서 메시지 수와 무관하게 무제한 증식.
- (참고: 2GB 파일 = 약 134개 청크.)

## 4. 데이터 모델 (DB 스키마)

```sql
-- 사용자
users(id, username, display_name, role)            -- admin / member

-- 폴더 트리
folders(id, name, parent_id NULL, owner_id)

-- 파일(논리적 메타데이터)
files(
  id,
  name, size, mime,
  folder_id,
  owner_id,
  created_at, updated_at
)

-- 실제 데이터 조각 (Telegram 맵핑) ★ 핵심
parts(
  id,
  file_id,          -- FK → files.id
  part_index,       -- 0,1,2,...
  offset,           -- 청크 시작 바이트
  part_size,
  tg_message_id,    -- Telegram 메시지 id (무결성/추적용)
  tg_file_id,       -- ★ 다운로드 시 사용
  checksum          -- 선택: sha256 무결성 검증
)

-- 권한 (20명용)
permissions(
  id,
  scope,            -- 'user' | 'group'
  scope_id,         -- user_id 또는 group id
  folder_id,
  role              -- 'read' | 'write' | 'admin'
)
```

## 5. 핵심 흐름

### 업로드
```
1. 클라이언트가 파일 업로드 → 서버가 수신
2. 서버가 15MB 단위로 분할 → 각 청크 생성(임시 디스크 or 메모리)
3. 청크마다 Telegram sendDocument 전송 (속도제한 큐로 스로틀링)
4. 각 응답에서 tg_file_id 확보 → parts 행 insert
5. 모든 청크 완료 후 files 행 + 폴더/권한 반영 → 커밋
6. 임시 청크 정리
```

### 다운로드
```
1. 파일 열기 요청 → 권한 확인(DB)
2. parts 전부 조회 → part_index 순 정렬
3. 각 tg_file_id를 Telegram getFile로 수신
4. offset 순서대로 이어붙여 스트리밍 응답
5. (선택) 자주 읽는 파일은 캐시에 저장
```

### 삭제
```
1. 권한 확인
2. parts 삭제 (Telegram 메시지 삭제는 선택 — 저장소 무제한이므로 논리 삭제 권장)
3. files / 권한 정리
```

## 6. 기술 스택 후보

| 계층 | 옵션 A (서버리스, 간단) | 옵션 B (자체 서버) |
|---|---|---|
| 웹앱/API | **TypeScript + Cloudflare Workers** | Node.js(Express/Fastify) or Python(FastAPI) |
| 메타데이터 DB | Cloudflare D1 or Supabase | PostgreSQL / SQLite |
| 캐시 | Cloudflare R2 / CDN | 로컬 디스크 캐시 |
| 클라이언트 | 웹 UI (React/바닐라) | 웹 UI + (선택) rclone / S3 API |

> 개인 학습 목적이면 **옵션 B(간단한 Node/FastAPI + SQLite)** 가 디버깅·이해가 쉽고 배포 부담도 적다.
> 서버리스 실험을 원하면 옵션 A를 후속 단계로.

## 7. 단계별 개발 일정 (Milestones)

### M0 — 환경 셋업 (≈ 1일)
- Telegram 봇 생성(`@BotFather`), 토큰/채팅/그룹 준비.
- 저장소 스캐폴드, DB 마이그레이션 도구, 기본 프로젝트 구조.

### M1 — 최소 동작 (Vertical Slice) (≈ 2~3일)
- 단일 파일 업로드(청크 없이) → Telegram 저장 → file_id 기록.
- 단일 파일 다운로드 → 재조립.
- CLI 또는 최소 웹 폼으로 파일 원본 보존 확인.

### M2 — 분할/조립 (≈ 2~3일)
- 15MB 청크 분할 업로드(속도제한 큐 포함).
- 청크 조립 다운로드 + 무결성(checksum) 검증.
- 100MB 이상 파일로 손상 없음 확인.

### M3 — 폴더·권한 (≈ 2~3일)
- 폴더 트리 CRUD.
- users + permissions 모델, 로그인(간단 세션/JWT).
- 사용자별 읽기/쓰기 제한 동작.

### M4 — 웹 UI & UX (≈ 3~5일)
- 파일 목록/업로드/다운로드/공유 화면.
- 진행률 표시, 오류 처리, 캐시(선택).

### M5 — 폴리싱 & 배포 (≈ 2~3일)
- 동시 사용자(20명) 가정 부하/race condition 점검.
- 에러 핸들링, 로깅, (선택) 실서버 배포.

> 총 예상: **약 2~3주** (하루 2~3시간 기준, 개인 일정에 따라 유동)

## 8. 위험 & 고려사항 (Risks)

| 리스크 | 설명 | 대응 |
|---|---|---|
| **Bot rate limit** | 대용량 = 수백 msg, 제한 초과 시 밴 위험 | 업로드 큐 + 스로틀링(초당 제한), 재시도/백오프 |
| **다운로드 지연** | 청크 N개 = 텔레그램 N회 호출 | 자주 읽는 파일 캐시, 프리뷰만 먼저 스트리밍 |
| **사용 약관(ToS)** | "무료 백업/개인 저장"은 허용. **공개 배포·스크래핑·과도한 자동화**는 회색지대 | 팀 전용 비공개 그룹으로만, 규모 유지, 개인 용도 명시 |
| **약관/정책 변경** | 텔레그램이 통제 강화 시 데이터 접근 위험 | 원본 보유 정책(분산 백업), 로컬에도 주요 파일 |
| **파일 무결성** | 전송 중 손상 가능 | checksum 기록 + 다운로드 시 검증 |
| **권한 우회** | file_id 노출 시 텔레그램 경유 접근 가능 | file_id는 절대 DB 밖으로 노출 금지, 서버에서만 조립·스트리밍 |

## 9. 한계 & 솔직한 평가

- 이 설계는 **"무제한 저장"에 최적화**된 구조라 UX/권한/안정성은 성숙한 웹드라이브보다 떨어짐.
- 운영 관점에선 사실 **Google Drive / Nextcloud**가 더 나을 수 있으나, **개인 프로젝트로 배우고 재밌게 만들기**엔 아주 좋은 주제.
- 실서비스로 키우기보다 **학습·포트폴리오·팀 내부 가벼운 공유** 용도로 적합.
- 안정성이 중요해지면: Local Bot API 서버(VPS) 도입 → 4GB 파일, 더 빠른 속도로 확장 가능 (후속 단계).
